# Meridian: where it stands (2026-10-28)

This is the starting point for anyone who works on Meridian. It replaces `LAUNCHPAD.md`, which describes beta.13. Every number below was
measured on the tree it names. Nothing here is taken from an older document without a check.

**Evidence levels.** *Built*: the code exists. *Tested*: its fixture or unit tests pass. *Browser-checked*: it ran in a real browser in the
check named. *Live*: a real provider was called and the result recorded. Today nothing is live.

## 1. Short answer

- Meridian starts from a clean checkout with no `.env`, on an embedded database, and the Settings and setup screens work in a real browser
  (25 browser checks, all passing on the baseline).
- Typecheck, lint, the build and the test suites pass on the baseline.
- No provider has been called live. Publishing, billing and paid calls have never run against a real account.
- The video engine is the most complete back end, and its own dry acceptance is red today, for a reason the owner has to decide (section 7).
- The product is wide and overlaps itself. Three generation paths and two "Factory" names make it hard to see where a video or an ad is
  really made (section 6). That is the main source of mess.
- Today's change is tidying only. It removes unused code, consolidates the test infrastructure, and moves test helpers out of production
  folders. It changes no behaviour, no contract and no migration (section 8).

## 3. What the product is

**Screens** (48 route files under `src/routes`):

- *Account and setup:* `/login`, `/setup`, `/quickstart`, `/docs`, `/product`, `/settings`, `/integrations`, `/invite`, `/webhooks`,
  `/audit`, `/usage`, `/exports`, `/alerts`, `/notifications`, `/jobs`, `/orchestrator`.
- *Per brand* (`/brands/$brandId/...`): brain, products, pages, accounts, learning, calibration, market, intelligence, opportunities,
  factory, studio, content, library, reviews.
- *Content Factory:* `/content-factory`, admin only. It drives the video engine: a brief or a script, a reference video, and the run's
  decisions, shots, review and delivery.
- *API routes:* assets, auth, Drive OAuth, engine media, health, media links, OAuth callback, Shopify and generic webhooks.

**Evidence by area.** Settings and setup: built, tested, browser-checked. The video engine: built and tested on fixtures; not live. The
ad factory (`lib/meridian/factory`), studio, production, publishing, measurement and learning: built and tested on fixtures; not live. The
exports screen: CSV exports, built and tested. The Content Factory run board and the one-shot remake: built and tested on fixtures
(`docs/engine/CONTENT_FACTORY_STATE_2026-10-18.md`).

## 4. How the parts fit

```
browser
  -> routes (src/routes)                      TanStack Start, file-based
  -> components (src/components)              design system in components/ui
  -> server functions (createServerFn)        one *actions.ts per area; each checks the role and the tenant
  -> domain services (src/lib/meridian/<area>) the business rules
  -> Postgres (migrations/, 131 SQL files)    PGlite when DATABASE_URL is unset; refused in production

background
  worker (scripts/worker-entry.ts) and scheduler (scripts/scheduler-entry.ts) claim jobs from the Postgres queue

video engine (src/engine)
  stages as jobs on that queue; the orchestrator is a pure state machine (jobs/orchestrator.ts)
  the API the app calls is engine/api/index.ts
  the gateway (engine/gateway) is the only place that calls fetch; keys come from the credential resolver
  contracts are zod schemas in engine/contracts, versioned (engine-contracts@9)

credentials
  workspace keys live in the credential vault and are read by lib/meridian/credentials/resolve.ts
  deployment keys come from the environment; a names-only readiness report: npm run live:readiness

other
  sidecar/   local helper that reads public pages (docs/SOURCING_SIDECAR.md)
  vendor/    Python packages for an optional research tool (agent-reach, scrapling); not in the app's runtime path
  functions/ media functions (ffmpeg probe, cuts, frames, loudness) for the worker or an HTTPS host
```

The database choice is made in `src/lib/db-source.ts`. The embedded database is allowed only when `NODE_ENV` is explicitly `development` or
`test`. Every other case, including production and an unset `NODE_ENV`, throws unless `DATABASE_URL` is set. That is the one place that
enforces the rule that production fails closed without `DATABASE_URL`.

## 6. The mess, measured

**A. Modules that only tests import: 45.** Found with an import graph over every source file (the script is not in the repo; the
graph resolves relative and `@/` imports, and it reads dynamic imports written as literal strings). After section 8, 45 remain. They fall
into three groups:

- *Documented as a product path, but no product code calls them.* `gates/disclosure-gate.ts` and `gates/slop-craft-gates.ts` (the
  disclosure and craft gates the Bible asks for); `distribution/export-package.ts` (FACTORY.md calls it the manual delivery path); the engine's
  `ops/batch.ts`, `ops/concurrency.ts` and `ops/alerts-sql.ts` (Bible E6); `render/splice-run.ts` (the splice render, not built).
- *Feature code with no caller:* the learning modules (`fatigue`, `guardrails`, `organic-telemetry`, `parameters`), `studio/loop.ts`,
  `study/deep-study-service.ts`, `production/route.ts`, `production/rework-engine.ts`, `production/voice-director.ts`, `jobs/durable.ts`,
  `video/scene-frames.ts`, `flow/nodes.ts`, `grading/priors.ts`, `intelligence/cluster.ts`, `jev/calibration.ts`, `organic/*`,
  `quality/evidence.ts`, `shopify/reel-attribution.ts`, `calibration/report.ts`, `discovery/provenance.ts`, `factory/cost.ts`,
  `factory/render.ts`, `factory/benchmark-harness.ts`, `storage/filesystem.ts`, `vision/logo.ts`, `a11y/contrast.ts`, and the UI helpers
  `lib/progress/*`, `lib/create/steps.ts`, `components/settings/connection-state.ts`. Some of these may be exercised by scripts that the
  graph does not follow, so each one needs a check before it is deleted.
- *Engine modules with no production caller:* `engine/assets/firstLastFrame.ts`, `engine/jobs/review-decision.ts`,
  `engine/orchestrator/example.ts` (an example, not a module), `engine/render/recorded.ts`, `engine/review/take/gold.ts`.

NORTH_STAR rule 2 says a module nothing calls is wired or not merged. Each of these needs a decision from the owner: wire it into a product
path, or delete it. Deleting them is not done here, because some are the documented delivery requirements.

**B. Documented as done, but the product does not reach it.**

- *Export package.* FACTORY.md says the manual export package is the delivery path, implemented in `distribution/export-package.ts`. No
  product code calls that module. The Exports screen (`routes/_app/exports.tsx`) downloads CSV files instead.
- *Disclosure.* The Bible requires an AI disclosure gate. The engine carries disclosure flags in the manifest (`engine/deliver/manifest.ts`).
  The gate module has no caller, and the wording is an open owner decision (Bible 20.2).
- *Engine ops server functions.* `lib/meridian/engine-ops/actions.ts` (stage metrics and the dead-letter list, role-checked) has no caller;
  its service and tests are only reached through it. The Orchestrator screen does not use them.

**C. Configuration.** The repo has three good boundaries: the credential resolver for workspace keys, `db-source.ts` for the database, and the
names-only readiness report. It still has no single typed server configuration. 76 non-test source files read `process.env` directly, and
153 variables are named in `.env.example`. Two architecture tests guard this. `credentials/resolve.test.ts` keeps provider-key reads inside an
allowlist. The `env-example` test checks that every variable the non-test source and scripts read is listed in `.env.example`. They are the
right guards, but they can only enforce the boundary that exists.

**D. Test infrastructure.** Before this change there were two copies of the Node test alias hook, and 27 test helpers sat inside production
folders (a `testing/` folder in `lib/meridian`, and fixtures beside production code). Section 8 fixes both. One exception remains by design:
`lib/meridian/decisions/recorded-decision-catalog.ts` is the recorded OpenRouter catalogue that the testing runtime uses through
`decisions/test-seam.ts`. It is data, and the runtime, not the tests, reads it.

**E. Root and docs clutter.** A long planning prompt sat at the repository root (moved to `docs/planning/`). `LAUNCHPAD.md` describes beta.13
and migrations up to `0107`; it is now superseded. `docs/engine/CHECKPOINT_2026-10-17_final.md` says PDF text is not read; the code reads it
(`content-factory/service.ts`). Three overlapping product documents (`FACTORY.md`, `CONTENT_PAGE.md`, `CONTENT_FACTORY_PLAN.md`) describe the
same work.

**F. Names.** "Factory" is the ad pipeline (`lib/meridian/factory`). "Content Factory" is both NORTH_STAR's name for that pipeline and the
`/content-factory` page that drives the video engine (`lib/meridian/content-factory`). "Studio" (`lib/meridian/studio`) and "production"
(`lib/meridian/production`) are two more generation paths. This naming is the single biggest source of confusion, and it is the first thing
a new contributor gets wrong.

**G. Large files.** The seven largest non-test files (section 5) each mix several responsibilities. They are the refactor candidates, and
each has a natural seam (for example the orchestrator's stage handlers, and the studio session's steps).

## 7. Live gaps and open decisions

- **The engine's dry acceptance is red, and that is correct under the current policy.** `npm run engine:e1 -- --dry-run` fails on one check,
  `ledger_bill_settles_render_cost`. The HyperFrames price per minute is unset, so a render has no provider bill, and its cost stays unknown
  until the owner records the invoice (`engine/render/STATUS.md`). Every other check passes. Whether a dry run should prove a bill is an
  owner decision, set out in `docs/FIRST_TEST_RUN.md`, step 6.
- **No live run of any provider.** OpenRouter (decisions, video and speech), Deepgram, Google Drive, the media functions host, Meta, TikTok,
  Google, Instagram, YouTube, Shopify, Apify and the search providers are all unverified against a real account (`docs/ROADMAP.md`).
- **Owner decisions still open** (`docs/LAUNCHPAD.md` lists them with their reasons): the render fallback, the narration defaults, video-DNA
  frame labelling, alerts for held calls, six-decimal bills, the lip-sync and avatar vendors, whether text files go to Drive, and the prices the
  engine will not guess (HyperFrames per minute, Apify per 1,000 results, `image.edit`). The Deepgram project rule is now in code: the key
  must see exactly one project.
- **Not verified here:** the PostgreSQL-only tests and `docker compose up --build`.

## 8. What changed today

Behaviour is unchanged. Contracts and migrations are unchanged.

1. **Removed unused code.** `src/lib/env.server.ts` (superseded by `db-source.ts` and the credential resolver) and
   `src/lib/meridian/intelligence/combinations.ts` (no caller). Both are recoverable from git history.
2. **One test alias hook.** `src/test-support/alias-hooks.mjs` is the more complete of the two copies. It is the only one now.
3. **Test helpers moved out of production folders.** The 20 test files and helpers of `src/lib/meridian/testing/`, and six test fixtures from
   `src/lib/meridian/`, moved to `src/test-support/`, keeping their paths under it. `src/engine/plan/fixtureInputs.ts` moved to `src/engine/test/`. The recorded OpenRouter
   catalogue moved to `src/lib/meridian/decisions/recorded-decision-catalog.ts`, because the testing runtime needs it. 358 import specifiers
   were rewritten in 164 files, and the two architecture-test allowlists were updated to the new path.
4. **The root planning prompt moved** to `docs/planning/CLAUDE_CODE_NEXT_PHASES.md`. Nothing refers to it.
5. **Documentation.** This document, `docs/FIRST_TEST_RUN.md` (the runbook), a superseded notice on `LAUNCHPAD.md`, the docs index, and a
   changelog entry.

Not changed, on purpose: the 45 test-only modules (section 6A), the E1 acceptance rule (section 7), the Postgres checks, and every product
path.
